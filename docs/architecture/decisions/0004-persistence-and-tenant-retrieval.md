# 0004 — Versioned persistence and tenant-filtered exact retrieval

Date: 2026-10-20. Status: accepted for milestone 03.

Milestone 02 storage is expanded through immutable forward SQL. Drizzle models cover organizations, memberships, credentials/integrations, customers, tickets/messages, documents/versions/chunks, drafts, normalized citations, jobs, receipts and audits. Soft deletion applies to mutable business entities. Audit and idempotency history is retained; `expires_at` marks receipt retention eligibility without silently changing replay behavior.

Customers are backfilled from existing ticket emails, then a tenant FK and validated non-null requirement are added. Compatibility triggers populate customers, version revisions, chunk ordinals/hashes and normalized citations for the previous API's writes. Ticket email snapshots and draft JSON citations remain during rolling upgrades; reads use normalized citations. Invalid historical evidence is excluded from normalized references and invalidated. No old column is dropped. Removing adapters and compatibility fields requires a separate contract migration after all old binaries retire.

Tenant-aware FKs prevent relationships crossing organizations, including the deferred active-version pointer and citations' full document/version/chunk identity. RLS protects domain tables for non-owner roles. Scoped repositories also retain explicit organization predicates. Transactions use `set_config(...,true)` to avoid pooled context leakage. Two bounded pre-tenant authentication lookups remain global: a hashed opaque credential and an integration UUID. Runtime has read-only access to those lookup tables; subsequent membership/organization validation occurs inside tenant context. They are not exposed as generic queries.

Publication locks the document and version, requires a processing replacement and complete model-compatible vectors, supersedes the previous version and commits the active pointer plus audit together. Repeated publication of the current version is harmless. Missing evidence, invalid state or a later SQL failure leaves the old publication intact. Version deletion removes its active pointer and audits atomically. Lexical, vector and evidence-approval queries independently require a live document, live chunk, live indexed version and matching active pointer. Stored citations remain historical evidence after deletion, but cannot authorize new approval.

The selected embedding model is the implemented **synthetic** SHA-256-derived fixture algorithm with exactly 64 normalized outputs. Its identity and dimension are explicit in environment configuration, Drizzle, SQL metadata and vector storage. It provides repeatable isolation/ranking tests; it makes no semantic quality claim. Real provider selection and generation remain milestone 06. Changing the model or dimension requires parallel storage/reindexing and an explicit migration, not an environment-only DDL change.

Retrieval materializes authorized candidates using a partial composite tenant B-tree, then computes exact cosine distances in pgvector with UUID tie-breaking. A global approximate index can underfill tenant-filtered results because filtering occurs after approximate scanning. The small fixture corpus does not justify approximate retrieval. Future scale work must measure tenant sizes, consider partitioning/per-tenant ANN and record recall before changing this choice. No latency or scale target is claimed.

References: [Drizzle pgvector models](https://orm.drizzle.team/docs/extensions), [pgvector exact search and filtering](https://github.com/pgvector/pgvector#filtering), [Faker reproducibility](https://fakerjs.dev/guide/usage.html#reproducible-results). Faker 9.9.0, a local Faker instance, a fixed seed, fixed reference date, stable IDs and timestamps make complete seed rows repeatable. No records are imported from external customers.

Domain processors and the durable failed-job DLQ remain milestone 04. Existing failed `job_runs` fixtures illustrate a failed replacement while retaining the old publication; they do not claim a functioning retry/DLQ pipeline.
