# Repository and registry protection checklist

These are repository/organization settings, not settings that a committed YAML file can enforce. No remote settings were changed by milestone 07.

- [ ] Protect `main` with a ruleset: PRs required, at least one independent approval, stale approvals dismissed, approval after the latest push, conversations resolved, and code-owner review for workflows, Dockerfiles, contracts and migrations. Assign real maintainers in repository CODEOWNERS/settings before relying on this item.
- [ ] Require the `Required checks` status emitted by **ResolveHub CI**, with the GitHub Actions app as the expected source. Select the exact displayed context after its first PR run. It aggregates quality, integration/coverage/migrations, dependency scan and container smoke. Require the branch to be up to date, or use the configured `merge_group` workflow with merge queues. Do not allow skipped/cancelled jobs to satisfy protection.
- [ ] Block force pushes and deletion; restrict direct pushes and bypass identities, including administrators. Restrict who can change repository Actions configuration, rulesets, environment protection and package permissions. Require signed commits if organizational policy supports them.
- [ ] Protect `v*` tag creation/update/deletion with a ruleset, restrict creators to release maintainers, and prohibit retagging. The workflow accepts stable `vMAJOR.MINOR.PATCH` pointing to a commit in protected main and rejects other tag forms. Tag rules matter because a workflow is read from the tagged commit.
- [ ] Create `ghcr-production` environment with deployment branch/tag restrictions for protected main and protected `v*` tags. Require independent release review and prevent self-review where available. Do not permit arbitrary feature branches/tags or bypasses. Verify these features are available for the repository's GitHub plan; gate releases externally if they are not.
- [ ] Set default workflow token permissions to read-only; disable Actions creating/approving PRs. Only the publish job requests `packages: write`; it uses `GITHUB_TOKEN`. Allow only required Actions and require full commit SHA pins. Keep hosted runner/action runtime updates under review.
- [ ] Require approval of workflows from external fork contributors. Never pass secrets/write tokens to PRs or enable `pull_request_target` to build their code. Do not execute untrusted PR artifacts in a privileged follow-up workflow. Avoid self-hosted production runners for PRs.
- [ ] Configure GHCR packages to inherit/link this repository, allow its publish workflow to write, restrict other writers, select private/public visibility intentionally, and grant deployment identities read-only access. Publish only unique run/SHA tags; deployment references must use digests. Retain previous digests and export manifests beyond the 90-day artifact lifetime.
- [ ] Enable Dependabot/advisory alerts and secret scanning/push protection where available. Review the visible unpatched `braces` development exception before **2026-11-21**. Any exception extension, available patch or newly reachable production path needs review; never globally suppress audit errors.
- [ ] Require backup/restore evidence and backward-compatible migration review before promotion. Confirm separate API/worker/migration identities, TLS, external secret-file permissions and a tested previous-digest rollback. Keep production credentials out of builds, PR jobs and repository files.
- [ ] Exercise first-run PR failure cases (drift, migration corruption, failing Jest/coverage, dependency finding and container failure), an unprotected-main/tag authorization denial, a successful protected-main/tag release, and a staging digest rollback. These remote behaviors need an actual configured GitHub repository and registry; local validation alone does not prove them.
